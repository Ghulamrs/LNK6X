**The verdict in one line.** asm6x + lnk6x is byte-identical to cl6x + lnk6x on 2 programs and
differs on 33 only in `.symtab`/`.strtab` - the same symbols in another order or string packing,
never in code, data, addresses or segments: the assembler is ratified on this corpus. LNK6x linked
**0 of 35** on RIDE's line (`rts6740_elf_eh.lib: cannot open`: `-i` is parsed and never
searched); a scratch copy taken through six additions (section B4) links 33 - and every image it
writes, like the bed's own q13 and q15 tonight, is **not an ELF file**: sections whose name is
not in its flags table are written at file offset 0, over the ELF header. What it takes, in the
order that unblocks the most, is section D.

## B. What each leg measured

**B1. asm6x + lnk6x against cl6x + lnk6x (35 programs): 2 identical, 33 equivalent.** 03-demo
and 04-projectile are byte-identical. The other 33 differ in `.symtab` (8 to 6,281 bytes) and
`.strtab` (50 to 29,469 bytes) only: `elfdiff` finds the same set of (name, value, section,
binding) on both sides, so what differs is the order lnk6x wrote the objects' local symbols in
and how it packed the string table - which follows the order asm6x wrote them in the object.
Every `.text`, `.const`, `.data`, `.cinit`, `.c6xabi.exidx/.extab`, every address, every segment
is the same. lnk6x is deterministic (q01 twice: identical).

**B2. LNK6x on RIDE's line (35 programs, 70 legs): 0 linked**, all on
`lnk6x: rts6740_elf_eh.lib: cannot open`. `-i` goes into `opt.libdirs` (`main.cpp:34`) and
nothing reads it; `-l name` is opened as a path (`link.cpp:70`). RIDE names the runtime by bare
name and gives two `-i` directories, as lnk6x takes it.

**B3. The bed tonight.** `make test`: 11 matched, 9 differed (six probes were added, below).
q05-model-rom, q07-lib, q10-ar and q16-ride stop on `not an ELF file` - archives are not read.
q09-subsect-named stops on `.text: no memory range for it` (the `{ *(.text:early) ... } > RAM`
form: the range after a brace list is read, but `.text:early` is then placed under its full
name). q12 stops on `.mybss: no memory range for it`. q14 on `unresolved symbol:
undefined_weak`. **q13 and q15 "differ" - and the files LNK6x wrote are not ELF: the first bytes
of q13's are `33 33 33 33`, the `.switch` word, and of q15's the trampoline probe's `.fartext`
code.** `image.cpp:66` lays out only sections with `SHF_ALLOC` in their *table* flags; `.const`,
`.switch`, `.cio`, `.stack`, `.sysmem` have 0 there (read off empty sections), and any name not
in the table gets 0 too (`.fartext`, `.mybss`, `.vm6747.eh`); their `offset` stays 0, and
`write_image` copies their bytes to `outs[c->out].offset + ...` = 0. A silent wrong image, which
the docs promise never to give. Every corpus program has `.const` bytes (476 of 810 objects).

So the chain to a *file that is an ELF executable* is: search, archives, linker-defined names,
subsections, COMMON, two relocation types, and the offset-0 fault. What is then still missing for
the image to be *right* is read off the oracle's maps and images (B5): the `.cinit` table
`--rom_model` asks for, `.stack`/`.sysmem` sizing, `.c6xabi.exidx` ordering, trampolines, the
attribute and section-flag records, the symbol table.

**B5. What the oracle's images say the rest of the way is** (RIDE's line, every program):
- `--rom_model` is inside the command file (`kTiLinkCmd` line 2) and `cmd.cpp:83` reads only
  `--stack_size` and `--heap_size` from a file: LNK6x links RIDE's programs as `--ram_model`
  without saying so. q16-ride is the probe (17,412 bytes with the runtime).
- **`.cinit`**: every program's map has 2-4 initialised sections compressed `rle` and a two-entry
  handler table `__TI_decompress_rle24`, `__TI_decompress_none`. q05-model-rom shows the shape at
  0xC00002E8: the compressed load image (first byte the handler index, here 0 = rle24, then
  the RLE stream), padding, `__TI_handler_table` (one 32-bit pointer per handler, 8 bytes),
  `__TI_cinit_table` (one record per initialised section: `{load address, run address}`, 8
  bytes each), with `__TI_CINIT_Base/Limit` and `__TI_Handler_Table_Base/Limit` bracketing
  the two tables. The runtime's `_c_int00` walks it. A linker that writes `none` images
  (uncompressed, handler index 1) is valid and differs from lnk6x's bytes; rle24 is TI's
  compressor (documented in the CGT user's guide) and is what byte-fidelity needs.
- `.stack` and `.sysmem` are sized from `--stack_size`/`--heap_size` (RIDE: 0x4000 and
  0x100000) and `__TI_STACK_END`, `__TI_STACK_SIZE`, `__TI_SYSMEM_SIZE` set; LNK6x parses both
  and allocates neither (`.stack` NOBITS, size 0 in every LNK6x image).
- The C++ programs bring `.c6xabi.exidx` (8,496 PREL31 relocations in the corpus, 271 EHTYPE)
  and `.c6xabi.extab`; lnk6x writes the index sorted by function address with
  `__TI_UNWIND_TABLE_END`... bracketing it; LNK6x has PREL31 (25) and EHTYPE (28) in neither
  `reloc.cpp` nor the enum.
- Trampolines: none needed by the corpus (0 in 35 maps: everything sits in one 64 MB range),
  q15 shows the shape when one is: `$Tramp$S$$faraway`, 32 bytes appended to `.text`
  (`STW B10,*B15--[2]` || `MVK`/`MVKH target,B10`; `B B10`; `LDW *++B15[2],B10`; `NOP 4`), and
  the map lists it under "trampolines".
- `.c6xabi.attributes` and `.TI.section.flags` are constants in `image.cpp`; the runtime's
  members carry five distinct attribute blobs (392/44/11/8/1 members) and lnk6x merges them
  (q05-rom's and q07's differ from the eight bare images'). q16's is the value RIDE's programs
  will need.
- The symbol table: 456 runtime members contribute locals; lnk6x's order (B1) follows input
  order, which LNK6x already does for objects.

**B6. What the six new probes settled (`tests/ref`, run tonight on the box).**
- **q11-pcr-mid**: a `CALLP` at offset 8 of its fetch packet - LNK6x matches byte for byte:
  PCR_S21 is packet-relative, `known.md`'s open question is closed.
- **q12-bss-order**: `.bss` at 0xC0000000 before `.text` (0xC0000040) again, `.neardata` after
  `.text` (0xC0000060), and `.mybss` - a `.usect` section the command file never names -
  **placed last, at 0xC0000064, in the only range**. The rule is about `.bss` by name, not
  about uninitialised or near sections; and an unnamed section is allocated after the named
  ones in the first range that fits. LNK6x refuses the unnamed one.
- **q13-const**: bytes in `.const`, `.rodata` and `.switch` - all three get `sh_flags` 2
  (ALLOC), where LNK6x's table says 0 for `.const` and `.switch` (read off empty sections).
  LNK6x's image is not ELF (B3).
- **q14-weak**: a strong `wk` in another object wins over the weak one (map: `wk` = the strong
  address); an undefined weak reference resolves to 0 and **stays in the symbol table as
  `UNDEF`, `WEAK`, value 0, with no error** (map: `UNDEFED undefined_weak`). LNK6x refuses it.
- **q15-far**: the trampoline above; LNK6x's image is not ELF (B3), and it has no trampolines.
- **q16-ride**: RIDE's command file with the runtime links q04 into 17,412 bytes: `.text`
  0x300, `.data`, `.cinit` 0x20 at 0xC0000308; `.vm6747.eh` is absent from the map (nothing
  contributes to it and lnk6x lists nothing for it). LNK6x: `not an ELF file` (archive).

**B7. Robustness (bad inputs, on the Mac).** An empty file, a 60-byte object, 65,535 sections,
a section table past the file, a text file as an object: refused with the file named
(`not an ELF file`, `broken section table`). A command file with no `MEMORY` block: refused. An
unterminated `MEMORY { ... ` block is accepted and the refusal comes later as `.text: no memory
range for it` - the wrong point of interception. **Two objects that both define `_c_int00`
link silently** (first wins); lnk6x refuses a redefinition. Nothing hung, nothing crashed.

**B8. The README's claims.** "One thread per input" is LINK's; this README does not claim it
and `read_inputs` is sequential (no `-pthread` in the Makefile) - fine. No mutable globals: true.
C++14 clean under all three flag sets: true. Diagnostics at the point of interception: true but
for the unterminated block and the silent duplicate.

### Not the linker's fault - found on the way, not edited (reported to the caller)

- `vm6747` cannot load an ELF `.out`, so nothing on the Mac or the box can *run* a linked C6000
  program: the TI legs are ratified by image comparison only. Loading a `.out` into the
  emulator (it has the ISA and the runtime model) would close that.
- asm6x's objects give lnk6x a different local-symbol order than cl6x's (33 of 35 images
  differ in `.symtab`/`.strtab` only) - harmless, but it is why "identical" is 2 and not 35.
- `kTiLinkCmd` names `.vm6747.eh` and not `.c6xabi.exidx`/`.c6xabi.extab`; lnk6x tolerates
  both (unnamed sections get default allocation), a stricter reading of the file would not.
- `RIDE/src/compile.cpp` writes the model into the command file; the compilers' drivers do the
  same. Any linker that reads options only from the line links `--ram_model` by mistake (N4 is
  LNK6x's, but the convention is worth knowing).
